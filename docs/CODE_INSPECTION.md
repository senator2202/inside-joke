# Инспекция кода: структура и наименования

> **Статус:** все 21 отклонение устранены в версии 0.8.0 (см. `CHANGELOG.md`). Отчёт описывает состояние 0.7.1.

Версия кода: 0.7.1. Проверены бэкенд (116 файлов Java в 10 пакетах), фронтенд (React + TypeScript), миграции БД,
конфигурация и переменные окружения, тесты, инструменты контроля стиля.

Ориентиры: соглашения Java (Oracle, Google Java Style), принятые в Spring роли и слои, соглашения Maven, REST-практики
(имена ресурсов, единая терминология), соглашения React и TypeScript, распространённые правила именования в PostgreSQL.

Приоритеты:

- **P1** — мешает сопровождению уже сейчас, стоит исправить в первую очередь;
- **P2** — отклонение от общепринятой практики, стоит исправить планово;
- **P3** — косметика или вопрос договорённости; исправить или записать как осознанное решение.

## Что уже соответствует стандартам

- Пакеты по функциям (`auth`, `billing`, `game`, `room`, `ai`, `admin`…), а не по техническим слоям.
- Внедрение зависимостей только через конструктор; нет `@Autowired` на полях, нет импортов со звёздочкой, нет
  `System.out`, нет забытых `TODO`/`FIXME`.
- Роли классов: все `@RestController` оканчиваются на `Controller`, `@Configuration` — на `Config`,
  `@ConfigurationProperties` — на `Properties`, репозитории — на `Repository`, `@Service` — на `Service`
  (проверяется `NamingConventionsTest`).
- Перечисления в единственном числе, константы в `UPPER_SNAKE_CASE`, ключи `application.yml` в kebab-case.
- БД: таблицы в единственном числе и snake_case, все временные поля `timestamptz` с окончанием `_at`, индексы с
  префиксами `ix_` / `ux_`, миграции Flyway `V{n}__описание.sql`.
- Тесты: `*Test` для модульных, `*IT` для интеграционных, все 162 тестовых метода бэкенда (195 запусков с
  параметризованными) названы в одном стиле — предложением в camelCase, вспомогательный код тестов в отдельном пакете `support`.
- Фронтенд: только именованные экспорты, нет `any` и `@ts-ignore`, классы CSS-модулей в camelCase, хуки называются
  `use…`, у каждой страницы есть тест рядом.
- Есть `.editorconfig`, `.gitignore`, checkstyle (32 правила) и ESLint без предупреждений.

## Бэкенд

### B1 (P1). `GameEngineService` — 1733 строки

Следующий по размеру класс — 380 строк. Обычная практика (принцип единственной ответственности, пороги Sonar и
аналогов) — несколько сотен строк на класс. В одном классе сейчас: жизненный цикл комнаты и лобби, анкета и секреты,
логика трёх видов раундов, голосование и очки, финал, пауза и переподключения, вызовы AI.

Рекомендация: оставить `GameEngineService` координатором (замок комнаты, переходы фаз) и вынести обработчики:
лобби, анкета и досье, по классу на вид раунда (дуэль, «Кто из нас», «Правда или AI»), подсчёт очков и финал,
пауза и соединения. Поведение и протокол не меняются. Работа крупная; риск средний, его снижают 195 тестов.

### B2 (P1). SQL вне репозиториев

Принятая в Spring схема слоёв: контроллер → сервис → репозиторий; SQL — только в репозиториях.

| Класс | Запросов SQL |
|---|---|
| `admin/AdminController` | 1 — **SQL прямо в контроллере** |
| `admin/AdminMetricsService` | 12 |
| `admin/PassReportService` | 6 |
| `admin/AiReportService` | 3 |
| `common/AppSettingsService` | 2 |
| `billing/PaymentService` | 1 |
| `billing/GameAccessService` | 1 (блокировка `pg_advisory_xact_lock`) |

Кроме того, отчёты админки читают таблицы биллинга и AI напрямую, в обход модулей, которым эти таблицы принадлежат.

Рекомендация: перенести запросы в репозитории (`AdminMetricsRepository`, `PassReportRepository`,
`AiCallRepository.search(...)`, `AppSettingRepository`, `EntitlementRepository.lockUser(...)`). Контроллеры не
должны знать о `JdbcClient`.

### B3 (P2). Контракты API вложены в сервисы и контроллеры

| Класс | Вложенных публичных записей |
|---|---|
| `game/Projector` | 16 — это весь контракт протокола WebSocket (`RoomView` и его части) |
| `billing/GameAccessService` | 7 |
| `admin/AdminMetricsService` | 7 |
| `admin/PassReportService` | 6 |
| `admin/AiReportService`, `admin/AdminController`, `auth/AuthController` | по 5 |

Типы, которые видит клиент, живут внутри классов с логикой: контракт трудно найти целиком, а любая правка сервиса
задевает файл контракта. Суффиксы ответов разнобойные: `Status`, `Summary`, `PassRow`, `CallSummary`, `Metrics`,
тогда как запросы единообразно называются `…Request`.

Рекомендация: вынести контракты в подпакеты (`game/protocol`, `admin/api`, `billing/api`) отдельными файлами и
принять суффиксы: `…Request` для входа, `…Response` или `…View` для выхода.

### B4 (P2). Классы не в своих пакетах

- В `auth` лежит вся почта: `EmailSender`, `SmtpEmailSender`, `ResendEmailSender`, `LogEmailSender`,
  `MailProperties`, `EmailMessage`. Почта нужна не только входу — выделить пакет `mail`.
- `common` стал «ящиком для всего»: веб-настройки (`WebConfig`, маршруты SPA), сервис флагов
  (`AppSettingsService`, `SettingKey`), ограничение частоты (`RateLimiter`), публичный статус (`StatusController`),
  утилиты (`Db`, `Tokens`, `ClientIp`). Разделить: `web`, `settings`, `ratelimit`; в `common` оставить общие ошибки
  и утилиты.
- `admin` читает чужие таблицы (см. B2).

### B5 (P2). Исключения без суффикса `Exception`

`AiService.InvalidOutput` и `PaymentService.Unprocessable` наследуют `RuntimeException`. По соглашениям Java имена
исключений оканчиваются на `Exception` (так же проверяют Sonar и IntelliJ). В проекте остальные исключения этому
следуют: `ApiException`, `AiCallException`, `EmailSendException`.

Рекомендация: `InvalidOutputException`, `UnprocessableEventException`.

### B6 (P3). Имена компонентов во множественном числе

`GoogleClients`, `JsonSecurityHandlers`, `LoginEvents` — один компонент, а имя во множественном числе, как у
коллекции. Варианты: `GoogleClientRegistrations`, `JsonSecurityHandler`, `LoginEventPublisher`.

### B7 (P3). Полные имена классов прямо в коде

`java.util.Currency`, `java.math.BigDecimal` в `PaymentService`, `java.util.function.ToLongFunction` в
`GameEngineService`, `org.springframework…Autowired` в `GoogleLoginIT`. Принято импортировать; полное имя — только
при конфликте имён.

### B8 (P2). Имена в адресах API

- **Одно понятие — два слова.** Интерфейс и `GET /api/admin/passes` говорят «пасс», а
  `GET /api/billing/entitlements`, `POST /api/admin/users/{id}/entitlements` и
  `POST /api/admin/entitlements/{id}/revoke` — «entitlement». В БД таблица `entitlement`. В API стоит оставить одно
  слово (разумно `passes`, как в интерфейсе).
- **Ещё одна пара терминов:** `POST /api/games/{sessionId}/feedback` — в адресе «игра», в параметре «сессия».
- **Число:** коллекции в REST называют во множественном числе (`/rooms`, `/games`), а `POST /api/audience/{key}` и
  `GET /api/audio/{id}` — в единственном.
- **Приемлемо как есть:** действия отдельными POST-адресами (`…/revoke`, `…/replay`, `/admin/drain`) — это
  распространённый паттерн «пользовательских методов» (Google AIP-136), и в проекте он применён единообразно.
  Отсутствие версии в пути (`/api/v1`) допустимо, пока API использует только свой фронтенд.

Переименование адресов — поломка контракта: по `docs/VERSIONING.md` это MINOR с пометкой **Breaking**.

## Тесты

### T1 (P2). Интеграционные тесты запускает Surefire

По соглашению Maven `*Test` запускает Surefire в фазе `test`, а `*IT` — Failsafe в фазе `integration-test`.
Сейчас Surefire запускает все 195 тестов, поэтому `mvn test` всегда поднимает PostgreSQL и Spring, и быстрые
модульные тесты не отделить от медленных.

Рекомендация: подключить `maven-failsafe-plugin` для `*IT`; `./mvnw verify` по-прежнему запустит всё.

### T2 (P3). Базовый класс `IntegrationTest`

Абстрактный базовый класс назван как тест. Принято `AbstractIntegrationTest` или `IntegrationTestBase`: имя не
совпадает с шаблонами поиска тестов и сразу говорит, что это основа, а не тест.

## База данных

### D1 (P2). Ограничения то с явными именами, то с автоматическими

Миграции V3–V4 называют ограничения явно (`ck_entitlement_revoke_reason`, `ck_purchase_refund_kind`…), а в V1–V2
20 проверок `CHECK`, 12 внешних ключей и все первичные ключи получили имена от PostgreSQL
(`purchase_status_check`, `entitlement_user_id_fkey`). Явные имена по единой схеме упрощают сообщения об ошибках
и будущие миграции.

Рекомендация: схема `pk_`, `fk_`, `ck_`, `ux_`, `ix_` + таблица + поле; переименовать существующие одной
миграцией (`ALTER TABLE … RENAME CONSTRAINT`), без изменения данных.

### D2 (P3). Булевы поля названы по-разному

`game_session.is_free` и `ai_call.is_free_game` обозначают одно и то же, но названы по-разному;
`entitlement.granted_by_admin` — без префикса `is_`. Выбрать один стиль. Переименование затронет код и запросы;
делать вместе с D1 или записать как исключение.

## Конфигурация

### C1 (P2). Разнобой префиксов переменных окружения

| Префикс | Переменные |
|---|---|
| `APP_` | `APP_PUBLIC_URL`, `APP_ALLOWED_ORIGINS`, `APP_ADMIN_EMAILS` |
| без префикса | `COOKIE_SECURE`, `SUPPORT_EMAIL` (при этом тоже настройки приложения) |
| `AI_` | `AI_REQUIRE_LLM_MODERATION` (рядом с `ANTHROPIC_…` и `TTS_…`) |

`PORT`, `DATABASE_…` и префиксы внешних сервисов (`PADDLE_`, `SMTP_`, `GOOGLE_`…) — общепринятые, их трогать не
нужно. Рекомендация: `APP_COOKIE_SECURE`, `APP_SUPPORT_EMAIL`, старые имена оставить как синонимы на один-два
релиза, иначе это поломка конфигурации.

### C2 (P3). Не всё описано в `.env.example`

`ANTHROPIC_BASE_URL` и `RESEND_BASE_URL` читаются из `application.yml`, но не описаны. Лимиты комнаты
(`APP_GAME_ROOM_TTS_BUDGET` и соседние) настраиваются только через неявную привязку Spring и нигде не упомянуты.

## Фронтенд

### F1 (P2). Модули со строчной буквой и десятком компонентов

| Файл | Строк | Компонентов |
|---|---|---|
| `pages/screen/scenes.tsx` | 487 | 7 |
| `pages/play/phoneScenes.tsx` | 440 | 11 |

Принято: компонент — в файле с именем в PascalCase, один основной компонент на файл. Рекомендация: каталоги
`pages/screen/scenes/` и `pages/play/scenes/` с файлами `LobbyScene.tsx`, `VotingScene.tsx`, `AnswerPhone.tsx` и т. д.

### F2 (P2). Скопированные вспомогательные функции

`errorText` и `formatDate` — одинаковые в `AiTab.tsx`, `PassesTab.tsx`, `PaymentIssues.tsx`. `Pagination`
экспортируется из `PassesTab.tsx` и импортируется оттуда соседями. Рекомендация: `pages/admin/format.ts` и
`pages/admin/Pagination.tsx`.

### F3 (P2). Типы контракта API написаны вручную

`lib/game/types.ts` повторяет записи сервера (`Projector.RoomView` и др.), `pages/admin/adminApi.ts` — ответы
админки. При изменении сервера типы легко разойдутся, и компилятор этого не заметит. Принятая практика —
генерировать типы из описания API (OpenAPI через springdoc, затем генератор TypeScript) или хотя бы сверять их
контрактными тестами.

### F4 (P3). Админка не локализована

8 файлов админки — на английском, тогда как весь продукт переведён. Это было осознанное решение (внутренний
инструмент); его стоит записать в `docs/CONVENTIONS.md`, чтобы не выглядело недоделкой.

### F5 (P3). Пустой случайный каталог

`frontend/src/{styles,components,pages/host,pages` — пустой каталог, оставшийся от команды `mkdir`, которую оболочка
не раскрыла. В архивы он не попадает (они собираются из файлов), но виден в рабочей копии и в IDE. Удалить.

## Инструменты и договорённости

### X1 (P2). Нет автоформатирования; checkstyle проверяет не все имена

Стиль держится вручную: нет форматтера для Java (google-java-format или Palantir через Spotless) и для
TypeScript/CSS (Prettier). Checkstyle проверяет имена типов, методов, констант и пакетов, но не полей, параметров,
локальных переменных, аббревиатур (`AbbreviationAsWordInName`) и порядка импортов (`CustomImportOrder`).

Рекомендация: добавить эти правила в checkstyle, подключить Spotless и Prettier, один раз переформатировать проект
отдельным изменением без правок логики.

### X2 (P3). Язык комментариев и документации

Код и комментарии — на английском, документация и журнал изменений — на русском. Это нормальная практика, но она
нигде не записана. Зафиксировать в `docs/CONVENTIONS.md`.

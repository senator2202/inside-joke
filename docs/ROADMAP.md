# Дорожная карта

Открытые вопросы после 0.8.2 и тестового рефакторинга: инженерный аудит (`docs/ENGINEERING_AUDIT.md`, коды вроде
S3, D6, O7), аудит безопасности (`docs/AUDIT.md`, номера пунктов), оценка по SOLID и горизонтальное масштабирование.
Сделанный пункт удаляется отсюда, а в `CHANGELOG.md` появляется запись о нём.

Приоритеты: **P0** — до запуска; **P1** — ближайшие итерации; **P2** — планово; **P3** — по возможности.

## Этап 0. До запуска

**R1 (P0). CI (аудит O1).** Конфигурации CI в проекте нет. `./mvnw verify` уже проверяет формат, checkstyle, тесты
и покрытие — его осталось запускать на каждое изменение. Готово, когда проверка обязательна для слияния в основную
ветку.

**R2 (P0). Образ для деплоя (O2).** Нет `Dockerfile` и описания окружений; `docker-compose.yml` поднимает только
базу. Готово, когда приложение собирается в образ и запускается с переменными из `.env.example`.

**R3 (P0). Пароль БД по умолчанию (O6).** В основном `application.yml` у `DATABASE_PASSWORD` есть значение по
умолчанию, и в продакшене оно тихо подставится. Готово, когда значение по умолчанию есть только в профиле `local`,
а без переменной сервер не стартует.

**R4 (P0). Режим почты `log` вне локальной разработки (O6).** `MAIL_PROVIDER=log` пишет в лог письмо целиком, с
действующим кодом входа. Готово, когда вне профиля `local` сервер с этим режимом не стартует.

**R5 (P0). Открытые пункты P1 аудита безопасности:**

- №8 — IP клиентов за Cloudflare: доверенные прокси, иначе лимиты по IP станут общими;
- №16 — роль администратора остаётся в живой сессии после исключения адреса из `APP_ADMIN_EMAILS`;
- №19 — нет предела копий экрана на комнату;
- №35 — докупленный третий пасс встаёт поверх второго;
- №36 — будущий (докупленный) пасс не виден хосту;
- №40 — нет Wake Lock: общий экран засыпает и включает автопаузу.

Готово, когда каждый пункт закрыт и отмечен в `AUDIT.md`.

**R6 (P0). Актуализировать `AUDIT.md`.** Пункт №34 (чарджбэк не отзывает пасс) исправлен в 0.3.2, но отмечен
открытым.

**R7 (P1). Базовые метрики (O4).** Наружу выведен только `health`. Нужны Micrometer и Prometheus: число комнат и
игроков, задержка команд, сбои и стоимость вызовов AI, очереди отправки WebSocket. Без них нельзя сделать R20.

## Этап 1. Архитектура и SOLID

**R8 (P1). Strategy по виду раунда (OCP, SRP).** Новый вид раунда сейчас требует правок в четырёх классах: ветвления
по `RoundKind` в `VotingPhaseHandler` (5), `RoomProjectionService` (5), `RoundPhaseHandler` (4), `RoundState` (1).
Нужен интерфейс вида раунда с операциями «сгенерировать контент», «принять ответ», «подвести итог голосования»,
«показать клиенту». Готово, когда новый вид раунда — это новый класс плюс контент и промпт, без правок существующих.

**R9 (P1). Разделить сервис AI (D1, ISP, N2).** `HostAiServiceImpl` (564 строки) совмещает промпты, HTTP, разбор
ответа, бюджеты, модерацию и голос; интерфейс `HostAiService` — шесть разнородных операций, а клиенты берут одну-две
(`RoomProjectionService` зависит от всего сервиса ради `secretsCheckable()`). Разделить по ролям: генерация контента,
модерация, голос. Реализации назвать по сути, без `Impl`.

**R10 (P1). Админка через сервисы модулей (S3).** `AdminController` внедряет чужие репозитории напрямую и имеет 12
зависимостей. Готово, когда контроллер говорит только с сервисами и разделён по разделам админки.

**R11 (P2). Таймеры и пауза вне координатора (D1, SRP).** `GameEngineService` — 927 строк и 14 зависимостей: API
комнат, таблицы команд и фаз, таймеры, пауза и переподключения, жизненный цикл. Вынести планировщик с дедлайнами и
паузу в отдельные классы.

**R12 (P2). Разделить `GameRuntimeService` (ISP).** 15 методов, а обработчики фаз используют от 4 до 11. Разделить
на контекст фазы (время, фоновые задачи, реплики) и переходы между фазами.

**R13 (P2). Инверсия зависимостей там, где она окупается (DIP).** WebSocket-транспорт — через узкий интерфейс движка
(«принять команду», «подключить участника») вместо конкретного `GameEngineService`; аналитика из биллинга и игры —
через события, как удаление аккаунта.

**R14 (P2). Подпакеты `game` (S2).** Разложить по назначению: `game.engine`, `game.phase`, `game.state`,
`game.content` (`game.dto` уже есть).

**R15 (P2). Длинные списки параметров (D6).** Конструктор `AiCallEntity` на 12 параметров, записи на 16–21 поле.
Объекты-параметры и значения.

**R16 (P3). Проверка параметров страниц и фильтров (D7).** Bean Validation (`@Min`, `@Max`) или общий компонент
вместо статического `PassReportService.checkPage`, который вызывает соседний сервис.

**R17 (P3). Единый язык предметной области (N1).** В API и интерфейсе — «пасс», в коде и БД — «entitlement»; так же
«игра», «сессия игры» и «комната». Переименовать `Entitlement*` в `Pass*` (таблицу — миграцией) и записать глоссарий в
`CONVENTIONS.md`.

**R18 (P3). Читаемость имён (N3, N4).** Однобуквенные параметры `r`, `m`, `p` в ядре игры; ручные типы фронтенда
названы иначе, чем DTO сервера.

## Этап 2. Масштаб и надёжность

**R19 (P1). Записать решение о состоянии в памяти (O3).** Все комнаты живут в памяти одного процесса. Нужен ADR:
почему так, сколько комнат выдерживает экземпляр, как деплоить через режим слива.

**R20 (P1). Нагрузочный тест одного экземпляра.** k6 или Gatling по WebSocket на реалистичных комнатах (8 игроков,
экран, зрители в режиме стримера). Зависит от R7. Готово, когда известны предел экземпляра и узкое место (ожидаемо —
вызовы AI и рассылка зрителям, а не процессор).

**R21 (P2, если R20 покажет нехватку). Горизонтальное масштабирование шардированием по комнатам.** Сейчас второй
экземпляр сломает игры: комнаты, токены и ключи зрителей — в памяти (`RoomRegistryService`); WebSocket подключается к
`/ws` без кода комнаты (`GameSocketHandler`); клипы озвучки — в памяти синтезировавшего экземпляра
(`VoiceLineCacheService`); уникальность кодов проверяется только в своём процессе; `RoomClosingListener` закрывает
только свои комнаты; `RateLimitService` считает лимиты в памяти. Шаги:

1. код комнаты во всех адресах: WebSocket, озвучка, ключ зрителя;
2. реестр владельцев комнат в PostgreSQL — заодно уникальность кодов по всему кластеру;
3. маршрутизация по реестру (одного хеширования мало: при добавлении экземпляра живые комнаты должны остаться у
   владельца);
4. команды между экземплярами (удаление аккаунта, действия админки) — через `LISTEN/NOTIFY` или брокер;
5. общий ограничитель частоты (Bucket4j на PostgreSQL или Redis) или ограничение на балансировщике;
6. живая статистика — метриками со всех экземпляров (R7) вместо `liveStats`.

**R22 (P2). Отказоустойчивость.** Падение процесса обрывает все его игры. Периодические снимки состояния комнаты, чтобы
после падения игру можно было поднять на другом экземпляре.

## Этап 3. Фронтенд, документация, инструменты

**R23 (P2). Разделение бандла (O7).** Один бандл на 463 КБ, админка загружается каждому игроку. Ленивая загрузка по
маршрутам.

**R24 (P2). Крупные компоненты (O7).** `AdminPage`, `PassesTab`, `ScreenPage`, `AiTab` — по 370–500 строк.

**R25 (P2). Загрузка данных (O7).** `useEffect` с флагами отмены повторяется из вкладки во вкладку; взять TanStack
Query или общий хук.

**R26 (P2). ADR и обзорная схема (O8).** Решения, которые нигде не обоснованы: состояние в памяти (R19), JDBC без ORM,
самописные генератор типов, ограничитель частоты и кэш озвучки, WebSocket вместо SSE.

**R27 (P3). Проверка доступности (O7).** Подключить `eslint-plugin-jsx-a11y`.

**R28 (P3). Сгенерированные типы напрямую (O7, N4).** Импортировать типы из `contract.gen.ts` вместо ручных копий,
которые сейчас только сверяются с ними.

**R29 (P3). OpenAPI (O8, D8).** Описание HTTP API через springdoc; генератор типов фронтенда тогда можно заменить
стандартным.

**R30 (P3). Обновления зависимостей (O9).** Dependabot или Renovate.

**R31 (P3). Типизированный SQL.** Если ошибки в SQL-строках станут заметной проблемой — jOOQ (типизированный SQL из
схемы, без потери возможностей PostgreSQL). Причины выбора JDBC вместо JPA — в ADR (R26).

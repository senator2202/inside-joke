# Инженерный аудит Inside Joke 0.8.1

> **Статус (0.8.2):** устранены S1 и D4 (циклы модулей: порт `GameAccessPort`, событие удаления аккаунта,
> `Language` в `common`, проверка `ModuleDependenciesTest`), D2 (инкапсуляция состояния игры), D3 (обработчики фаз
> через `GameRuntimeService`, без полей координатора и цепочек), D5 (перечисления вместо строк, в том числе в SQL),
> из D1 — разбор команд и `roundView`, из раздела «Паттерны» — Command, State и Value Object (`Money`). Остальное
> открыто.

Взгляд со стороны: код прочитан как незнакомый. Проверены 189 классов Java, фронтенд (React + TypeScript),
миграции, сборка, тесты и готовность к эксплуатации. Выводы опираются на измерения: зависимости между модулями,
размеры и ветвистость классов и методов, доступ к полям, типизация, тестовая пирамида, артефакты сборки.

Приоритеты: **P0** — закрыть до запуска; **P1** — ближайшие итерации, мешает развитию; **P2** — планово; **P3** — по
возможности.

## Итог

Код аккуратный на уровне «строк»: единые имена и формат, проверяемые автоматически, нет скопированных блоков, нет
пустых `catch`, время берётся из инъецируемого `Clock`, SQL только в репозиториях, контракт API генерируется и
сверяется с фронтендом. Слабые места — на уровне архитектуры и процесса: модули зависят друг от друга по кругу, модель
игры — открытые изменяемые поля, координатор и его обработчики сцеплены в обе стороны, половина решений держится на
строках вместо типов. Процессно проект не готов к командной разработке и эксплуатации: нет Git, CI, образа для
деплоя, метрик; правила игры проверяются только медленными интеграционными тестами; все игры живут в памяти одного
процесса.

## 1. Именование

Сильная сторона. Роль класса видна по суффиксу (`…Service`, `…Repository`, `…Dto`, `…Entity`, `…State`, `…Utils`), и
это проверяет `NamingConventionsTest`; имена ограничений БД и булевых полей проверяет `SchemaIT`.

**N1 (P2). Два слова для одного понятия внутри кода.** Клиенту и в интерфейсе — «пасс» (`/api/billing/passes`,
`PassStatusDto`, `PassLogRepository`), а в коде и БД — «entitlement» (`EntitlementEntity`, `EntitlementRepository`,
таблица `entitlement`). Так же «игра», «сессия игры» и «комната»: `GameSessionRepository`, `gameSessionId`,
`/api/games/{gameId}`, `RoomState`. Единый язык предметной области (DDD) должен быть одинаков в коде, API и БД.
Рекомендация: переименовать `Entitlement*` в `Pass*` (таблица — миграцией) и записать глоссарий в
`docs/CONVENTIONS.md`.

**N2 (P3). `HostAiServiceImpl`.** Суффикс `Impl` при единственной реализации — известный запах: имя не говорит, чем
реализация отличается. Интерфейс оправдан (тесты подменяют модель), но имя лучше по сути: `AnthropicHostAiService`.

**N3 (P3). Однобуквенные параметры в ядре игры.** В пакете `game` комната, участник и игрок передаются как `r`, `m`,
`p` в 94 параметрах против 21 с полными именами — при методах на 60–120 строк это заметно ухудшает чтение. Полные имена: `room`,
`member`, `player`.

**N4 (P3). Фронтенд говорит на своём словаре.** Ручные типы фронтенда названы иначе, чем DTO сервера: `RoomView` —
`RoomStateDto`, `PassRow` — `PassLogEntryDto`. Их совпадение по полям проверяется, но один контракт живёт под двумя
именами. См. также F4.

## 2. Пакетная структура

Пакеты по функциям — верный выбор. Проблема в том, что функции не отделены друг от друга.

**S1 (P1). Циклические зависимости между модулями.**

| Модуль | Зависит от |
|---|---|
| `admin` | ai, auth, billing, common, game, settings |
| `ai` | common, game, moderation, settings |
| `analytics` | auth, common, web |
| `auth` | billing, common, game, mail, web |
| `billing` | ai, analytics, auth, common, game, settings |
| `game` | analytics, billing, common, moderation, settings |
| `room` | analytics, auth, common, game, web |

Прямые циклы: `auth ↔ billing`, `billing ↔ game`. Через третьи модули — ещё: `game → billing → ai → game`,
`game → analytics → auth → game`. Модули нельзя понять, протестировать или выделить по отдельности; любое изменение
расходится кругами. Рекомендация — принцип инверсии зависимостей: ядро (`game`) объявляет порты (например,
«разрешено ли начать игру», «сообщить о событии») как интерфейсы, `billing` и `analytics` их реализуют. Направление
зависимостей записать и проверять автоматически (ArchUnit или Spring Modulith).

**S2 (P2). `game` — пакет «обо всём».** В нём движок, пять обработчиков фаз, изменяемое состояние, репозиторий,
интерфейс к AI, запасной контент, проекция в DTO — 37 файлов разных уровней (не считая `game.dto`). Подпакеты по назначению:
`game.engine`, `game.phase`, `game.state`, `game.content`, `game.dto`.

**S3 (P1). Админка в обход слоя сервисов.** `AdminController` внедряет чужие репозитории напрямую
(`EntitlementRepository`, `WebhookEventRepository`, `GameSessionRepository`) и имеет 12 зависимостей на 12
эндпоинтов. Контроллер должен говорить с сервисами модулей; сам он — разделить по разделам админки.

## 3. Принципы проектирования

**D1 (P1). Единственная ответственность в ядре нарушена.**

| Класс или метод | Размер | Что в нём смешано |
|---|---|---|
| `GameEngineService` | 959 строк, 23 публичных метода, 14 зависимостей | API комнат, разбор команд, планировщик, пауза, жизненный цикл |
| `GameEngineService.dispatch` | 121 строка, 20 строковых веток | маршрутизация всех команд WebSocket |
| `RoomProjectionService.roundView` | 199 строк, 49 ветвлений | представление раунда для всех ролей и фаз |
| `HostAiServiceImpl` | 564 строки | промпты, HTTP, разбор и проверка ответа, бюджеты, модерация, голос |

Рекомендации — в разделе «Паттерны» (Command, State, отдельные преобразователи) и: разделить `HostAiServiceImpl` на
сборку промптов, разбор с проверкой ответа, учёт бюджета и голос.

**D2 (P1). Модель без инкапсуляции.** `RoomState` — 43 изменяемых поля без `private`, `PlayerState` — 29,
`RoundState` — 11, `DuelState` — 8. Правила (например, «очки меняются только при раскрытии», «состояние меняют только
под замком комнаты») держатся на договорённости, а не на типах: любой класс пакета может нарушить их незаметно. Это
«анемичная модель» в худшем варианте — без инкапсуляции даже на уровне сеттеров. Рекомендация: поля `private`,
изменения — методами с проверкой инвариантов (`player.award(points)`, `room.startRound(...)`), коллекции наружу —
только для чтения.

**D3 (P1). Двусторонняя связь координатора и обработчиков.** Обработчики фаз держат ссылку на координатор, читают его
поля напрямую (`engine.clock`, `engine.fallback`… — до 31 обращения на класс) и вызывают друг друга цепочками
(`engine.voting.reveal(...)`). Координатор создаёт их в конструкторе, передавая `this`, — отсюда подавленное
предупреждение `this-escape`. Это нарушает закон Деметры и делает обработчики нетестируемыми по отдельности.
Рекомендация: общий узкий контекст (планировщик, контент, события, время) интерфейсом; переходы между фазами — через
координатор, а не друг через друга.

**D4 (P1). Инверсия зависимостей не соблюдена между модулями.** См. S1: `game` зависит от конкретного
`GameAccessService` из `billing`, а `billing` — от `game`.

**D5 (P2). Строки вместо типов.** Команды WebSocket — `switch` по строкам (20 веток). Статус покупки — строка
(`"REFUNDED"`, `"COMPLETED"` в Java и SQL), действия Paddle и итоги вызовов AI — тоже строки в сравнениях и
запросах. Опечатка компилируется и ломается в работе. Рекомендация: перечисления с привязкой к JSON и БД.

**D6 (P2). Длинные списки параметров и «широкие» записи.** `HostAiServiceImpl.record` — 12 параметров; записи на 21, 18
и 16 полей (`PassLogRepository.Entry`, `WebhookEventRepository.NotAppliedEvent`, `AiCallRepository.LoggedCall`).
Сумма и валюта везде передаются парой примитивов. Рекомендация: объекты-параметры и значения (`Money`, `RoomCode`).

**D7 (P3). DRY соблюдён, с одной скрытой связью.** Скопированных блоков нет. Но проверку параметров страницы
`AiReportService` берёт у соседнего `PassReportService.checkPage` — два отчёта связаны через статический метод.
Лучше Bean Validation на параметрах (`@Min`, `@Max`) или общий компонент пагинации.

**D8 (P3). KISS: несколько самописных решений там, где есть стандартные.** Генерация TypeScript из Java
(`ContractTypesTest`) вместо springdoc + OpenAPI-генератора; собственные ограничитель частоты и кэш аудио; ручная
проверка параметров запросов. Каждое работает и протестировано, но это код, который придётся сопровождать, — решения
стоит зафиксировать в ADR или заменить стандартными.

## 4. Паттерны

**Применены уместно:**

- **Repository** с чтением для отчётов (`PassLogRepository`).
- **Strategy через конфигурацию:** реализации `MailClient` выбираются `@ConditionalOnProperty`.
- **Observer:** `RoomEventListener` отделяет ядро от транспорта WebSocket.
- **Port и Adapter:** `HostAiService`; тесты подменяют модель через этот интерфейс.
- **Fallback:** `FallbackContentService` работает при сбое AI.
- **Facade:** `GameEngineService` для контроллеров.

**Не хватает там, где просятся:**

- **Command (P1).** Каждая команда WebSocket — отдельный обработчик в реестре «имя → обработчик» вместо `dispatch` на
  121 строку. Новая команда — новый класс, а не правка общего `switch`.
- **State (P2).** 79 проверок фазы в 7 файлах. Состояние-объект на фазу («что разрешено», «что по таймеру», «куда
  дальше») собрало бы правила фазы в одном месте. Обработчики фаз — полшага к этому, но переходы и проверки по-прежнему
  разбросаны.
- **Value Object (P2).** `Money`, `RoomCode`, `Email` вместо примитивов (D6).
- **Mapper (P2).** Проекция состояния в DTO — набор небольших преобразователей по частям (игрок, раунд, финал)
  вместо метода на 199 строк.

**Сомнительно:**

- **Реестр комнат-одиночка в памяти** (см. O3).
- **Доступ обработчиков к внутренностям координатора** похож на «локатор сервисов» (D3).

## 5. Прочее

**O1 (P0). Нет системы контроля версий и CI.** В проекте нет `.git`, нет конвейера сборки. Без этого невозможны ревью,
откат, история решений, защита основной ветки. `./mvnw verify` уже проверяет всё нужное — его осталось запускать на
каждое изменение.

**O2 (P0). Нет артефакта для деплоя.** Нет `Dockerfile` и описания окружений; `docker-compose.yml` поднимает только БД.

**O3 (P1). Все игры — в памяти одного процесса.** `RoomRegistryService` хранит комнаты в `Map`: перезапуск или деплой
обрывает все идущие игры, второй экземпляр приложения невозможен без «липкой» маршрутизации WebSocket. Режим слива
смягчает деплой, но не сбой. Для MVP допустимо — если это осознанное решение: записать в ADR с пределами (сколько
комнат выдерживает один процесс, как деплоить), и спланировать снимки состояния или вынос в Redis.

**O4 (P1). Наблюдаемость.** Наружу — только `health`. Нет метрик (Micrometer и Prometheus: число комнат, задержки
команд, сбои AI, очереди отправки), трассировки, структурированных логов. Бизнес-метрики есть только в админке через
SQL.

**O5 (P1). Тестовая пирамида перевёрнута.** 11 классов модульных тестов против 24 интеграционных; правила игры
модульно не тестируются вовсе — только через полный запуск приложения с БД. Итог: медленная обратная связь и
зависимость от времени (24 ожидания `Await.until`, 4 `Thread.sleep` в тестах; нестабильные тесты уже встречались).
Нет измерения покрытия (JaCoCo) и архитектурных тестов. Рекомендация: после D2 и D3 правила игры тестируются как
обычные классы, без Spring.

**O6 (P1). Безопасность.**

- В основном `application.yml` — пароль БД по умолчанию (`insidejoke`): в продакшене он тихо подставится, если
  переменная не задана. Значение по умолчанию должно быть только в профиле `local`.
- Режим `MAIL_PROVIDER=log` пишет письмо целиком — адрес и действующий код входа — в лог. Для разработки это задумано,
  но в продакшене режим ничем не запрещён: одна ошибка в конфигурации — и коды входа окажутся в логах. Запретить его
  вне профиля `local`.
- В `docs/AUDIT.md` открыты семь пунктов P1: IP клиентов за Cloudflare (№8), инъекция закрывающего тега в промпт (№9),
  роль администратора в живой сессии после исключения из списка (№16), нет предела копий экрана (№19), наложение
  докупленных пассов (№35), невидимый будущий пасс (№36), нет Wake Lock (№40). Сам документ устарел: чарджбэк (№34)
  исправлен в 0.3.2, но отмечен открытым.

**O7 (P2). Фронтенд.**

- **Один бандл на 463 КБ.** Админка грузится каждому игроку. Нужно ленивое разделение по маршрутам.
- **Крупные компоненты:** `AdminPage` (496 строк), `PassesTab` (400), `ScreenPage` (371), `AiTab` (367).
- **Загрузка данных вручную:** `useEffect` с флагами отмены повторяется из вкладки во вкладку. Стоит взять
  библиотеку (TanStack Query) или общий хук.
- **Нет проверки доступности:** не подключён `eslint-plugin-jsx-a11y`.
- **Сгенерированные типы контракта используются только для сверки.** Ручные типы дублируют их (см. N4). Лучше
  импортировать сгенерированные напрямую.

**O8 (P2). Документация решений.** Нет ADR и обзорной схемы архитектуры. Ключевые решения (состояние в памяти,
самописные генератор и ограничитель, WebSocket вместо SSE) нигде не обоснованы. Нет описания HTTP API (OpenAPI).

**O9 (P3). Гигиена зависимостей.** Нет Dependabot или Renovate: обновления, в том числе по безопасности, придётся
отслеживать вручную.

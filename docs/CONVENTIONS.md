# Соглашения о коде

Правила, которые можно проверить автоматически, проверяются: `NamingConventionsTest`, `SchemaIT`, checkstyle,
ESLint, Spotless и Prettier (см. «Форматирование»). Сборка с нарушением не пройдёт.

## Языки

- Код, комментарии в коде, сообщения логов и админка — на английском. Админка — внутренний инструмент команды,
  её не переводят.
- Интерфейс для игроков и хостов — на английском и русском, через словари `frontend/src/locales`.
- Документация (`README.md`, `docs/`, `CHANGELOG.md`) — на русском.

## Бэкенд

### Пакеты

Пакеты по функциям: `auth`, `billing`, `game`, `room`, `ai`, `moderation`, `analytics`, `admin`, `mail`, `settings`,
`web`. В `common` — только то, что нужно всем: ошибки API, `AppProperties`, `CoreConfig`, `DbUtils`, `TokenUtils`.

Данные, которые проходят через API, — в подпакете `dto` своего модуля (`admin.dto`, `auth.dto`, …), отдельными
файлами. Сообщения протокола WebSocket — тоже данные API, они в `game.dto` вместе с HTTP-ответами игры.

### Слои

Контроллер → сервис → репозиторий. SQL — только в классах `…Repository`, и только в репозитории модуля, которому
принадлежит таблица. Отчёт, которому нужны данные нескольких модулей, собирает их в сервисе из репозиториев этих
модулей.

### Зависимости между модулями

Модули (пакеты сразу под `com.insidejoke`) не зависят друг от друга по кругу — это проверяет
`ModuleDependenciesTest`. Если нижнему модулю нужно что-то от верхнего, он не импортирует его, а:

- объявляет порт — интерфейс, который верхний модуль реализует (`game.GameAccessPort` реализует `billing`);
- или публикует событие Spring, на которое верхние модули подписываются (`auth.AccountDeletedEvent`: `billing`
  отзывает пассы, `game` закрывает комнаты).

Понятия всего приложения (например, `Language`) живут в `common`.

### Ядро игры

- `GameEngineService` — координатор: API комнат, таблица команд, таблица фаз, планировщик. Логика фаз — в
  обработчиках `…PhaseHandler`. Они получают координатор только через интерфейс `GameRuntimeService` и свои
  зависимости явно в конструкторе, не читают полей координатора и не вызывают друг друга: переход в другую фазу —
  метод `GameRuntimeService`.
- Команды протокола — перечисление `CommandType` (имя в протоколе и нужное право) и по одному `CommandHandler` на
  каждую (паттерн Command). Завершение фазы по «дальше» и по таймеру — таблица `Phase → PhaseHandler` (State).
- Состояние игры (`RoomState`, `PlayerState`, …) — только приватные поля. Наружу — методы доступа; коллекции — только
  для чтения; изменения — методами с понятным смыслом (`putPlayer`, `addScore`). Чистые вычисления над состоянием
  (`standings()`, `rankOf()`) — методы самого состояния.

### Типы вместо строк

- Статусы, виды и коды — перечисления (`PurchaseStatus`, `PassLogStatus`, `AiOutcome`, `AdjustmentAction`, …). Внешние
  строки (события и статусы Paddle) разбираются в перечисление один раз, на входе; неизвестное значение — `OTHER`.
- Значения, которые могут быть `null`, передаются в `JdbcClient` по одному через `param(...)`: в Spring 7 пакет
  размечен `@NullMarked`, и у `params(...)` элементы по контракту не могут быть `null` (работает, но на это нельзя
  опираться, и IntelliJ предупреждает). Такие параметры и поля записей помечаются `@Nullable` из JSpecify.
- В SQL постоянные значения подставляются из перечислений: `DbUtils.sql(PurchaseStatus.REFUNDED)`,
  `DbUtils.sqlList(AiOutcome.FAILURES)` — никаких строковых литералов статусов в запросах.
- Деньги — значение `Money` (сумма в минимальных единицах и код валюты); арифметика только в одной валюте. В DTO сумма
  остаётся плоскими полями.

### Имена классов: по имени видно, данные это или логика

**Логика всегда несёт суффикс роли:**

| Суффикс | Что это |
|---|---|
| `Service` | Бизнес-логика, бин `@Service`. Реализация одноимённого интерфейса — `…ServiceImpl` (`HostAiServiceImpl`) |
| `Repository` | Доступ к данным (`@Repository` или реализация `…Repository` Spring) |
| `Controller` | HTTP API (`@RestController`) |
| `Client` | Вызов внешней системы: Anthropic, TTS, SMTP, Resend (`AnthropicClient`, `SmtpMailClient`) |
| `Config` | Конфигурация Spring (`@Configuration`) |
| `Handler` | Обработчик: колбэки фреймворка, фазы игры, команды, соединение WebSocket (`GoogleLoginSuccessHandler`, `IntakePhaseHandler`, `CommandHandler`) |
| `Listener` | Получатель событий (`RoomEventListener`) |
| `Utils` | Только статические методы (`DbUtils`, `ContentRuleUtils`) |
| `Exception` | Исключение |

**Данные несут суффикс вида данных или остаются существительным:**

| Суффикс | Что это | Пример |
|---|---|---|
| `Dto` | Всё, что проходит через API (HTTP и WebSocket); входящее тело — `…RequestDto` | `CreateRoomRequestDto`, `RoomStateDto`, `PageDto` |
| `Entity` | Строка таблицы БД, которую возвращает репозиторий | `PurchaseEntity`, `UserEntity` |
| `State` | Изменяемое состояние игры в памяти | `RoomState`, `PlayerState` |
| `Properties` | Настройки из `application.yml` | `MailProperties` |
| без суффикса | Прочие внутренние данные: записи, перечисления | `RoundContent`, `RoomSettings`, `Tone` |

Суффиксы `Dto`, `Request`, `Response` и `View` вне пакетов `dto` не используются. Имена в единственном числе.

Правила проверяет `NamingConventionsTest`: суффикс роли у каждого бина по его аннотации, `Service` только у
`@Service`, `Properties` у настроек, записи `…Dto` только в пакетах `dto`, `Utils` ровно у классов со статическими
методами, `Exception` ровно у исключений. Тестовый код следует соглашениям тестов (`Fake…`, `…Test`, `…IT`) и этой
проверкой не охвачен.

### Тесты

`*Test` запускает Surefire в фазе `test` (быстро, без БД), `*IT` — Failsafe в фазе `verify` (встроенный PostgreSQL
и всё приложение). Имена тестовых методов — предложением в camelCase: `aHiddenCodeNeverReachesTheStream`.

Тесты держат пирамиду: внизу много быстрых модульных, выше меньше интеграционных, наверху несколько сквозных.

| Уровень | Что проверяет | Как |
|---|---|---|
| Модульный (`*Test`) | Правила игры, проекции состояния, AI-шлюз, утилиты, соглашения | Без Spring, БД и сети, миллисекунды на тест |
| Интеграционный (`*IT`) | То, что живёт на стыке: HTTP и безопасность, протокол WebSocket, SQL и схема, вебхуки Paddle, почта, связка модулей | Всё приложение, встроенный PostgreSQL, внешние сервисы — `FakeHttp` |
| Сквозной (`GameFlowIT`) | Целая партия ботами по WebSocket, с AI и без | Как интеграционный |

- **Правило игры — модульный тест.** Новое правило или исправление в пакете `game` проверяется через `GameHarness`
  (`src/test/java/com/insidejoke/game`): настоящий движок и обработчики фаз, фальшивый AI-ведущий `FakeHostAi`,
  часы и таймеры, которые двигает только тест (`advance`, `expire`), фоновая работа на потоке теста (`hold` и
  `release` делают AI «опоздавшим») и случайность с фиксированным зерном. Партия играется за миллисекунды и каждый раз
  одинаково; ждать в реальном времени нельзя.
- **Интеграционный тест — только для стыка.** Правило, которое можно проверить модульно, в `*IT` не дублируется. `*IT`
  проверяет, что решение движка доходит до клиента или базы (кадр `kicked` и код закрытия, запись в `ai_call`), а не
  само решение.
- **Покрытие.** JaCoCo строит отчёт модульных тестов (`target/site/jacoco`) и общий (`target/site/jacoco-all`).
  Пакет `game` должен быть покрыт модульными тестами не меньше чем на 90 % строк и 75 % ветвлений — иначе фаза `test`
  падает. Порог не снижают, чтобы пропустить изменение: сначала тест.
- **Фронтенд.** Vitest в пуле `vmThreads`: один jsdom на поток, свежие модули на каждый файл.

## HTTP API

- Ресурсы — существительные во множественном числе, в kebab-case: `/api/rooms`, `/api/voice-lines/{id}`.
- Одно понятие — одно слово во всём API и интерфейсе: «пасс» (`passes`), «игра» (`games`), «комната» (`rooms`).
  В БД пассы хранятся в таблице `entitlement` — это внутренняя деталь.
- Действия, которые не сводятся к созданию или изменению ресурса, — POST на подресурс-глагол:
  `/api/admin/passes/{id}/revoke`.
- Поля JSON — camelCase; пустые поля протокола WebSocket не отправляются (`@JsonInclude(NON_NULL)`).
- Коды ошибок — `UPPER_SNAKE_CASE` в `ErrorCode`.
- Изменение адреса, поля или смысла — поломка контракта (см. [VERSIONING.md](VERSIONING.md)).

## База данных

- Таблицы в единственном числе, всё в snake_case; время — `timestamptz` с окончанием `_at`.
- Булевы поля — `is_…` или `has_…`; одно понятие — одно имя во всех таблицах.
- Имена ограничений и индексов: `pk_<таблица>`, `fk_<таблица>_<поля>`, `ck_<таблица>_<поля>`, `ux_…` (уникальные),
  `ix_…` (прочие индексы). Ограничения называются явно (`CONSTRAINT ck_…`).
- Миграции Flyway `V<n>__<описание>.sql`; выпущенную миграцию не меняют.

## Переменные окружения

- `APP_*` — настройки самого приложения; `DATABASE_*` и `PORT` — как принято у хостингов.
- Настройки внешнего сервиса — под его именем: `ANTHROPIC_*`, `TTS_*`, `PADDLE_*`, `SMTP_*`, `RESEND_*`, `GOOGLE_*`,
  `POSTHOG_*`.
- `AI_*` — политика AI, не зависящая от поставщика (например, `AI_REQUIRE_LLM_MODERATION`).
- Каждая переменная описана в `.env.example`. Переименование — со старым именем в роли синонима минимум на один
  релиз и записью в раздел **Deprecated** журнала.

## Фронтенд

- Компонент — в файле с его именем в PascalCase, один основной компонент на файл. Группа компонентов — каталог с
  `index.ts` (например, `pages/screen/scenes/`); общие типы и функции группы — в `shared.ts`.
- Хуки — `use…`; модули без компонентов — в camelCase (`billing.ts`, `format.ts`).
- Только именованные экспорты; без `any` и `@ts-ignore`.
- Классы CSS-модулей — camelCase.
- Тест лежит рядом с тем, что проверяет: `Имя.test.tsx`.
- Типы контракта API (`lib/api/contract.gen.ts`) генерируются из кода бэкенда и вручную не правятся.

## Форматирование

Java форматирует Spotless (palantir-java-format), TypeScript и CSS — Prettier. `./mvnw verify` проверяет формат;
исправить: `./mvnw spotless:apply` и `npm run format` во `frontend`.
